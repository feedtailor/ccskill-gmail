> **2026-06-11 再編成**: 起票時（2026-05-29）は「`ccskill-gmail`(管理) と `.ccskill-gmail/api`(操作) が別パスで紛らわしい」という問題だったが、#122-#125 のグローバル化で API CLI が `ccskill-gmail api` に統合され、問題の構造が変わった。本 issue を現状（同一 CLI の二段構造）に合わせて書き直す。旧記述は「出典・作業記録」に保存。

## 概要

ccskill-gmail には用途の異なる 2 系統のコマンドがあり、取り違えが繰り返し発生している。

| 系統 | 形 | 役割 | サブコマンド |
|---|---|---|---|
| **管理系** | `ccskill-gmail <cmd>` | セットアップ・設定・運用管理（人間が叩く） | `setup` / `install` / `account` / `bind` / `unbind` / `skill` / `migrate` / `info` / `status` / `history` / `doctor` / `update` 等 |
| **API 系** | `ccskill-gmail api <sub>` | Gmail への実操作（LLM が主に叩く） | `get` / `post` / `download` / `save-html` / `save-pdf` / `whoami` |

`api` を付ける/付けないで系統が分かれるが、この境界が直感的でないため、両方向の取り違えが起きる:

1. **管理コマンドを API 系の位置に置く**: `ccskill-gmail api unbind` / `ccskill-gmail api info`（→ Unknown subcommand）
2. **API コマンドを管理系の位置に置く**: `ccskill-gmail get action=...`（→ Unknown command）
3. **action をサブコマンドと取り違える**: `ccskill-gmail api search ...`（`search` は `get` に渡す action）

#117 / #118 で確立した原則 **「LLM はドキュメントを読み切らない。最も確実に効くのは実行時のフィードバック」** に従い、ドキュメント整備に加えて **CLI のエラーメッセージで隣の系統へ誘導する** ことを軸に対処する。

## 修正方針

### 必須

1. **API 系エラーで管理系へ誘導（lib/api）**
   `ccskill-gmail api <X>` の `<X>` が管理系コマンド名（`account` / `bind` / `unbind` / `skill` / `migrate` / `info` / `status` / `history` / `doctor` / `setup` / `install` / `update` 等）に一致する場合、汎用の Unknown subcommand ではなく **「`<X>` は管理コマンドです。`ccskill-gmail <X>` を使ってください（`api` は不要）」** を返す。
   - 出典の `api info`、2026-06-11 の `api unbind` がいずれもこの分岐で正しく案内される。

2. **管理系エラーで API 系へ誘導（ccskill-gmail ディスパッチャ）**
   `ccskill-gmail <X>` の `<X>` が API サブコマンド（`get` / `post` / `download` / `save-html` / `save-pdf` / `whoami`）に一致する場合、**「`ccskill-gmail api <X> ...` のことですか?」** と案内。
   さらに `<X>` が代表的な action 名（`search` / `get_thread` / `get_message` / `list_labels` / `get_profile` 等）なら **「`ccskill-gmail api get action=<X> ...` では?」** と案内。

3. **SKILL.md / SKILL.ja.md に二段構造の早見表**
   Quick Start 冒頭に上記の「管理系 / API 系」対比表を 1 つ置き、**「`info` / `status` / `history` / `bind` 等は管理系であり `api` の下では使えない」「逆に `get` / `post` / `whoami` は必ず `api` の下」** を名指しで明示。

4. **reference/index.md に get_profile を追記**
   Read Operations 表に `get_profile`（`ccskill-gmail api get action=get_profile` / アカウント・未読数を返す）を 1 行追加。`reference/read.md` に記述が無ければ併せて追記。

### 検討

5. **アカウント確認手段の集約**
   「アクティブアカウントの確認 = `ccskill-gmail api whoami`（解決経路も表示）／ 詳細は `ccskill-gmail account list` ／ プロフィールだけなら `api get action=get_profile`」を 1 か所に並べて提示。whoami の存在で旧来の `ccskill-gmail info` 依存より明快になっている。

6. **`account_source` で binding.json 由来とレガシーメタデータ由来を区別する**
   現状はどちらも `binding` と表示され、unbind 後にレガシーへフォールバックしたことが whoami から判別できない（2026-06-11 の実例: unbind 後も `binding` 表示のまま endpoint だけ旧専用デプロイに変わり、ユーザーが「unbind したのに binding のまま」と混乱）。案: レガシー側を `binding-legacy` にする、または whoami の data に解決元ファイルパス（binding.json / .ccskill-metadata.json）を追加する。レガシー掃除の手段は #126 側で扱う。
