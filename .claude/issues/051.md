## 概要

現在の `source .ccskill-gmail/api.sh && ccskill-get ...` パターンを廃止し、
単体実行可能なスクリプト `.ccskill-gmail/api` に置き換える。

## 背景

### 問題1: `&&` が正常系に含まれるセキュリティ懸念

現在のパーミッションパターン `Bash(source .ccskill-gmail/api.sh*)` は
`source .ccskill-gmail/api.sh && 任意のコマンド` を許可してしまう。
正常な使い方自体が `&&` を含むため、プロンプトインジェクションにより
`&&` 後に悪意あるコマンドが挿入されても、パターン上は区別できない。

単体スクリプトにすれば正常系から `&&` が消え、`&&` を含むコマンドが
生成された時点で異常な兆候として検知しやすくなる。

### 問題2: `source` の必要性

Claude Code の Bash ツールは呼び出しごとにシェル状態がリセットされるため、
`source` で読み込んだ関数・変数は次の呼び出しに引き継がれない。
そのため毎回 `source ... && ccskill-get ...` と書く必要があるが、
これは対話的シェルセッション前提の設計が Claude Code の実行モデルに
合っていないことに起因する。

### 問題3: UX の煩雑さ

- コマンドが長い（source + && + $GMAIL_ENDPOINT）
- SKILL.md に「source と && で繋げ」等のルール説明が必要
- $GMAIL_ENDPOINT がユーザーに露出する

## 設計

### Before / After

```bash
# Before
source .ccskill-gmail/api.sh && ccskill-get "$GMAIL_ENDPOINT" action=search query="is:unread"
source .ccskill-gmail/api.sh && ccskill-post "$GMAIL_ENDPOINT" '{"action":"create_draft",...}'
source .ccskill-gmail/api.sh && _gmail_download "$GMAIL_ENDPOINT" MSG_ID 0 /tmp/file.pdf
source .ccskill-gmail/api.sh && _gmail_save_pdf "$GMAIL_ENDPOINT" MSG_ID ./email.pdf
source .ccskill-gmail/api.sh && _gmail_save_html "$GMAIL_ENDPOINT" MSG_ID ./email.html

# After
.ccskill-gmail/api get action=search query="is:unread"
.ccskill-gmail/api post '{"action":"create_draft",...}'
.ccskill-gmail/api download MSG_ID 0 /tmp/file.pdf
.ccskill-gmail/api save-pdf MSG_ID ./email.pdf
.ccskill-gmail/api save-html MSG_ID ./email.html
```

### スクリプト構造

```bash
#!/bin/bash
# .ccskill-gmail/api — ccskill-gmail 単体実行スクリプト

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"

# 初期化（現在の _ccskill_init と同等）
source "$SCRIPT_DIR/../.env"        # GMAIL_ENDPOINT
source "$SCRIPT_DIR/auth.sh"        # gas_token

# エンドポイント検証（現在の ccskill-assert-endpoint と同等）
# URL エンコード（現在の ccskill-encode と同等）

# サブコマンド振り分け
case "$1" in
  get)       shift; # 現在の ccskill-get ロジック ;;
  post)      shift; # 現在の ccskill-post ロジック ;;
  download)  shift; # 現在の _gmail_download ロジック ;;
  save-pdf)  shift; # 現在の _gmail_save_pdf ロジック ;;
  save-html) shift; # 現在の _gmail_save_html ロジック ;;
  *)         echo '{"ok":false,"error":"Usage: .ccskill-gmail/api {get|post|download|save-pdf|save-html} ..."}' ;;
esac
```

## sandbox による `.env` 読み取りブロック問題

Claude Code の sandbox は `**/.env` をデフォルトで読み取り拒否する。
現在の `_ccskill_init` は `source "$project_root/.env"` で `GMAIL_ENDPOINT` を読み込むため、
sandbox 有効時に `$GMAIL_ENDPOINT` が空になり API 呼び出しが失敗する（b2bios-bizmobile で実際に発生）。

単体スクリプト化により `.env` の読み込み方法を見直す機会となる。検討候補：
- `.ccskill-gmail/endpoint` 等の非 `.env` ファイルに endpoint を分離（sandbox の拒否パターンを回避）
- スクリプト内で `.env` を `grep` + `cut` で読む（`source` を避ける）
- install 時にスクリプト内に endpoint を埋め込む

いずれの方法でも、sandbox を無効化せずに動作することを完了条件に含める。
