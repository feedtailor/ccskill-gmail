## 概要

`status` / `update-all` / `info` は、共有セットアップ（`binding.json` のみ・専用 GAS なし）のディレクトリを**永久に outdated と誤判定**し、`update-all`（専用 GAS の個別追従更新）を促す。版数判定を mode 別に分岐し、専用 GAS のレガシー install が残っている場合は `update-all` 一辺倒でなく**集約（`migrate`）を促す**ようにする。

## 多エージェント議論の裁定 (2026-06-16)

指摘 A は実コードで全面的に裏付けられた**実在の欠陥**。維持（KEEP 相当）。ただし severity は **最高 → 高** に補正。理由: データ破壊・セキュリティ影響はなく、api 本体（検索・閲覧・下書き）は無傷。`status`/`update-all`/`info` を能動実行したときだけ表面化する**表示・誘導バグ**。

## 確定した事実（コード根拠）

- 共有セットアップ install は central 分岐（`install.sh:126-236`）で完結し `.ccskill-metadata.json` を一切書かない（メタデータ生成は dedicated 専用の `install.sh:417`）。
- `registry_upsert` は metadata 不在時に `version="unknown"` を恒久記録（`registry.sh:108`）。
- `MASTER_VERSION` は git short HEAD（`VERSION` ファイルは実在しない）。`"unknown"` との一致は原理的に不可能。
- `status.sh:194` / `update-all.sh:85` / `info.sh:107` は version 文字列の単純一致のみで central/dedicated を区別せず、共有セットアップを恒久 outdated 誤判定。
- `update.sh:283` の central 分岐は `registry_upsert` を再実行するが metadata を書かないため version は `"unknown"` 固定で自己修復しない一方、直後の `L290` で「Updated to version: …」と実バージョンを表示する自己矛盾。
- `update-all.sh:151-154` は `deployment_id` 不在を理由に MANUAL_DEPLOY_NEEDED へ積み、`L187-204` で「GAS エディタで手動デプロイ」を誤提示（`update.sh:274`「共有 GAS は account update が管理」と矛盾）。

## 実装内容

1. registry エントリに **mode（central / dedicated）** を持たせる（または `binding.json` の有無 = `update.sh:272` が既に使用 する条件で判別）。
2. `status` / `update-all` / `info` / `update` の版数比較を mode 別に分岐。共有（central）は版数比較対象外とし、表示に `shared` / `per-project` を出す。
3. `update-all.sh:151-154` の `deployment_id` 空判定を central モードでは MANUAL_DEPLOY_NEEDED に積まない。
4. 専用 GAS（per-project）が残る場合、`status` の Tip を `update-all` 一辺倒でなく **`migrate`（集約）主体**に。`update-all` の Tip は個別運用継続者向けに格下げ（消さない）。
- **旧 `.ccskill-metadata.json` 最優先解決の後方互換経路は壊さない。**

## スコープ外 / 用語

- 「中央化 / central」は使わない。「共有セットアップ / 集約」で統一する。
