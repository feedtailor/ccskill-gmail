## 概要

`examples.md` に新しいワークフローパターン（#18）として、未返信メールからタスク候補を抽出する手順を追加する。

## 背景・経緯

todo-tracker スキルとの連携で「朝イチにメールを確認し、未返信メールからタスク候補を抽出して todo.txt に追加する」というワークフローを試行した。その際に以下の問題が発生した。

### 発生した問題

1. **search 結果から thread ID を jq で除外してしまった**
   - `jq '.data.threads[] | {subject, from, date, snippet}'` と書き、`id` を含めなかった
   - そのため件名で再検索する必要が生じ、類似件名の別スレッド（ダウンロード通知メール）を誤って掴んだ
   - 結果、本来は返信済みのスレッドを「未返信」と誤判定した

2. **未返信判定には get_thread で最終送信者の確認が必要**
   - search のレスポンスだけでは「自分が最後に返信したか」がわからない
   - get_thread を並列実行して最終メッセージの `from` を確認する手順が必要

### 検討した代替案

| 案 | 内容 | 判断 |
|----|------|------|
| A: 新アクション `check_reply_status` を追加 | threadId を複数渡して未返信判定を一括で行う | 見送り。利用頻度が未確定の段階で API を増やすのは過剰。頻繁に使うことがわかったら改めて検討 |
| B: search レスポンスに `lastSender` を追加 | 各スレッドの最終送信者を search 時に返す | 見送り。`thread.getMessages()` を全スレッド分呼ぶためパフォーマンス劣化のリスクあり |
| C: examples.md にワークフローとして記載 | Claude 側の運用手順として文書化 | **採用**。API はシンプルに保ち、まず運用で回してから判断する |

### 決定理由

- API はシンプルに保つ方針を優先
- examples.md は既に17パターンのワークフロー集として機能しており、ここに追加するのが最も自然
- 運用実績を積んでから、必要に応じて専用アクション（案A）への昇格を検討する

## やること

`examples.md` に以下の内容でワークフロー #18 を追加する。

### 記載すべき内容

1. **目的**: メールから未返信スレッドを抽出し、タスク候補として提示する
2. **重要な注意点**: search 時に jq で `id` を必ず含めること（今回の事故の再発防止）
3. **手順**:
   - search で未読メール or 直近メールを取得（`id` を含む）
   - get_thread を並列実行して各スレッドの最終送信者を確認
   - 最終送信者が自分（ユーザーのアドレス）でないスレッド = 未返信と判定
   - 自動通知系（noreply等）を除外
   - 未返信スレッドをタスク候補として一覧提示
4. **具体的なコマンド例**: 実際に使える search + jq + get_thread のコマンド例
5. **判定ロジックの補足**: 自分のアドレスの判定は `get_profile` で取得可能であることにも言及

### 参考: 今回実際に使ったフロー

```bash
# Step 1: 未読メール検索（id を必ず含める！）
.ccskill-gmail/api get action=search query="is:unread" maxResults=20 | jq '.data.threads[] | {id, subject, from, date}'

# Step 2: 各スレッドの最終送信者を確認（並列実行）
.ccskill-gmail/api get action=get_thread threadId=THREAD_ID | jq '.data.messages[] | {from, date}'

# Step 3: 最終送信者が自分でないスレッドを「未返信」として抽出
# → Claude が from フィールドを確認し、自分のアドレスでなければ未返信と判定
```
