## ユースケース概要 — loop ポーリング運用

ユーザーは `/ccskill-gmail loopでワークフローを見ながらよろしくです` というコマンドで、エージェントが20分ごとに Gmail を巡回し、新着メールを以下の方針で処理する運用を行っている:

1. `newer_than:1h` で新着検索
2. 検出メールをワークフロー定義 (`.claude/workflows/`) と照合
3. プロモ/通知メールは AskUserQuestion で4択提示 (既読+アーカイブ / 既読のみ / アーカイブのみ / 何もしない)
4. ワークフロー該当はその処理を実行
5. 業務メールは保持

このコマンド自体は ccskill-gmail スキルに含まれない、ユーザー個別の運用パターン。

## 直面した課題

24時間運用の中で複数の判断ミス・ルール変更が発生:

### 課題1: プロモ自動アーカイブの対象範囲がブレる
当初「Dell Rewards 等の自動配信プロモは確認なしでアーカイブ」というルールで開始したが、note の通知メール（朝メモ等）まで誤ってアーカイブし、ユーザーから訂正された。さらに後から「全部4択で確認する方針に変えたい」と方針自体が変更された。

### 課題2: `newer_than` の落とし穴 (詳細は #107)
ユーザーが下書き作成・送信予約したスレッドが「新着」と誤検出され、AskUserQuestion を発してしまった。`newer_than` がスレッドの最終更新時刻を見るため。

### 課題3: 同じパターンの作業を毎セッション再学習している
- プロモ判定 (どのドメインが自動配信か)
- 業務メールの保持判定 (人間からの送信か)
- ワークフロー照合 (どのメールがどのワークフローに該当するか)

これらは毎回 LLM 推論で判断しており、**判断の再現性が弱く、コストもかかる**。

## なぜ "memory に書く" では不十分か

実際にこのセッションでも `feedback_loop_promo_autoarchive.md` 等の auto-memory に積み重ねていったが、以下の問題がある:

- **解釈の揺れ**: 自然言語のメモはエージェントによって解釈が分かれる。例えば「自動配信プロモ」の境界は note を含むか含まないかで揉めた
- **適用漏れ**: メモは「読み込まれて初めて効く」ため、新セッションでは関連メモを引かないと無視されうる
- **デバッグ困難**: 「なぜこのメールがアーカイブされたか」を後追いするには会話履歴を漁るしかない
- **方針変更時の影響範囲不明**: ルールを書き換えても、既に動いている loop に即時反映される保証がない

つまり memory は「エージェントの判断を支援するヒント集」止まりで、**運用ルールの実行責任はエージェント側に残ったまま**。

## レシピで解決したい姿

#102 のレシピ構想を読み直すと、まさにこのケースを解くための仕組みに見えます。具体的には:

```yaml
# 例: ftgmail/recipes/loop-poll.yaml (イメージ)
trigger:
  schedule: "*/20 * * * *"  # 20分ごと
  query: "newer_than:1h"
guards:
  # #107 の newer_than 落とし穴対策
  - skip_if: hasDraft
  - skip_if: lastSentMessage.from == self
  - skip_if: lastSentMessage.date > now
match_rules:
  - id: workflow-direct-maintenance
    when:
      from: support@l-is-b.com
      subject_contains: メンテナンス
    action: invoke_workflow(redmine-direct-maintenance)
  - id: promo-googleworkspace
    when:
      from_domain: apps-telecom.jp
      subject_starts_with: 【Googleアップデート】
    action: ask_4choice(default=archive)
  - id: keep-note-morning-memo
    when:
      from: noreply@note.com
      subject_contains: 朝メモ
    action: keep
default_action: ask_4choice
audit:
  log_to: ftgmail/loop-audit.jsonl
```

この形なら:

- **ルールの実行責任が recipe runner に移る** → エージェント世代交代しても挙動が変わらない
- **判断ブレが消える** → "プロモかどうか" を毎回 LLM 推論しなくて済む（ルールに書いた条件で決定論的）
- **方針変更が一点修正で済む** → recipe を編集するだけ
- **audit ログで追跡可能** → 「なぜアーカイブされた / されなかった」を後追いできる
- **コスト削減** → ルールマッチで処理できるメールは LLM 推論を経由しない

## レシピ枠組みへの要望（実装者へのインプット）

#104, #105 の設計時に以下を考慮いただけると、こうした loop 運用ケースに耐えられる枠組みになると思います:

### 必須に近いもの

1. **guard 機構 (前置フィルタ)** — `hasDraft` / `lastSentMessage` 等のスレッドメタ情報で除外できる仕組み。`newer_than` の落とし穴を含む各種誤検出を recipe 側で吸収できる
2. **match → action の明示的マッピング** — 1メールに複数ルールがマッチした場合の優先順位 (first-match / most-specific / 明示優先度) を事前に決めておく
3. **action の語彙** — `mark_read` / `archive` / `keep` / `ask_user(<choices>)` / `invoke_workflow(<name>)` / `create_draft` の最低6つは欲しい
4. **audit ログ必須** — 「どのルールがマッチしてどう動いたか」を記録。recipe-creator が後でこれを学習材料にできる

### あると嬉しい

5. **trigger の多様性** — schedule (cron風) だけでなく、on-demand 呼び出し、特定キーワード受信時の即時起動、等
6. **default_action の明示** — どのルールにも該当しない場合に何をするか (LLM トリアージへフォールバック / 何もしない / 通知だけ)
7. **dry-run モード** — recipe 変更時に「もし適用したらこの10件はこう処理される」をシミュレーション
8. **recipe-creator (#105) との接続** — audit ログから「ユーザーが ask_4choice で毎回同じ選択をしているルール」を検出し、「default を archive に固定しませんか？」と提案

### スコープ外でも検討したい

9. **プロジェクト固有 recipe vs ユーザー共通 recipe の階層** — `~/.ccskill-gmail/recipes/` (グローバル) と `<project>/.ccskill-gmail/recipes/` (プロジェクト) を分けて、loop 運用のような特殊ケースをプロジェクトに閉じ込められるように
