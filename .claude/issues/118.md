## 概要

ユーザーから「返信下書きをさせたのにスレッドが切れて新規メールになっていた」報告があり、当該 AI の自己分析で以下の構造的問題が判明した:

1. `create_draft` に `threadId` を渡してもスレッドに紐付かない (パラメータが存在しないので無視される) が、その**明示が無い** ため LLM が「渡してみれば動くかも」と推測する余地がある。
2. `create_reply_draft` で `to` を指定しても無効 (GmailApp API 制約) だが、その**明示が create_reply_draft 側に無い** ため LLM が「to で上書きできるはず」と試行錯誤する。注意書きは `update_draft` L296 にだけ存在し参照が分散している。
3. `create_reply_draft` の `skipSelf: true` / `replyAll: true` のデフォルト挙動の説明はあるが、**典型失敗例 (社内 → 社外スレッドで To が社内人物に固定される)** が書かれていない。

#117 で実証された通り、**「重要制約は関連箇所に重複記載しないと LLM は辿り着かない」**。本 issue で draft 系 API のリファレンスを強化する。

## 出典

2026-05-14、別 AI セッションでの自己分析報告。「社内(藤田) → 社外(柴田)」のスレッドへの返信下書き作成で、To が社内(藤田)に固定される現象が発生 (`skipSelf:true` で最新の他人 = 藤田が選ばれた結果)。当該 AI は最初に `to` パラメータで上書きを試み、続いて `create_draft` に `threadId` を渡してスレッド化を試み、いずれも失敗した。

## 実装内容

### 必須

1. **`reference/draft.md` の `create_draft` セクションに「`threadId` は存在しない」明示**

   現状: パラメータ表に threadId なし。L58 で "For replies to existing threads, use `create_reply_draft`" とは書いてあるが弱い。

   追加文 (案):
   > **Note**: `create_draft` does NOT accept a `threadId` parameter. Passing it has no effect — the API will silently ignore it and create a stand-alone (non-thread) draft. For thread replies, use `create_reply_draft`; this is the only way to attach a draft to an existing thread.

2. **`reference/draft.md` の `create_reply_draft` セクションに「`to` は指定不可」明示**

   現状: パラメータ表に to が無いだけで、明示的な禁止文が無い。update_draft L296 にのみ書かれている。

   追加文 (案、Behavior Details の前後):
   > **Note**: `to` is NOT a valid parameter for `create_reply_draft`. The recipient is computed from the thread context according to `skipSelf` / `replyAll` (see Behavior Details below). If the auto-selected recipient is not what you want, **edit it in Gmail UI after the draft is created** — there is no API path to change it.

3. **`reference/draft.md` の `create_reply_draft` Behavior Details に「典型失敗例」セクション追加**

   現状: L237-241 で skipSelf の挙動説明はあるが、失敗パターンは未記載。

   追加内容 (案):
   ```markdown
   ### Common pitfall: internal → external thread

   When a thread mixes internal and external participants, the auto-selected
   recipient may not match user intent.

   Example: thread is `you → internal_colleague → external_partner` (chronological).
   With `skipSelf: true`, the API skips your own messages and picks the **most recent
   non-self message** — which is `internal_colleague`. The draft's `To` becomes the
   internal colleague, not the external partner.

   If the user wants to reply to the external partner instead:
   - Create the draft as-is, then **ask the user to swap To/Cc manually in Gmail UI**
   - There is no API parameter to override this — `to` is rejected (see Note above)
   ```

4. **`SKILL.md` / `SKILL.ja.md` に短い Critical Rule を追加 (検討)**

   `<important if="you are about to create a draft">` 的なブロックは過剰なので、Rules When Calling セクションに 1 行か、または既存 Critical Rules ブロックに 1 行追加する方向。文言案:

   > **For thread replies, always use `create_reply_draft`** — `create_draft` does not accept `threadId`. **`to` is not a valid parameter for `create_reply_draft`** — the recipient comes from the thread context (see [reference/draft.md](reference/draft.md)).

   配置検討: Email Review Critical Rules セクションの末尾、または独立した小セクション。**長くしすぎないことが重要**。

### スコープ外

- `skipSelf` / `replyAll` のデフォルト挙動を変えること (API 仕様変更は別 issue)
- `create_reply_draft` で To を上書きする機能拡張 — reply 系 GmailApp メソッド (`createDraftReply` / `createDraftReplyAll`) の options に `to` が存在しないため、現状の実装では不可。raw MIME ドラフト (Gmail Advanced Service) なら **追加 OAuth 権限なし** で実現の余地はあるが、dependency 追加・GCP 連携・MIME メンテの複雑性コストに見合わないため見送り。要望 (「スレッド末尾配置」と「To=相手」の両立) と見送り判断の経緯は #119 に記録
