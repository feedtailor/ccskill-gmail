## 概要

指摘 B（危害モデル補正後）と、指摘 E から切り出した permission 撤去漏れを扱う。中核は **`account remove` の default 自動昇格による silent-misrouting**（binding を持たない default 依存ディレクトリが**無警告で別アカウントへルーティング**される）。

## 多エージェント議論の裁定 (2026-06-16)

- 指摘 B = **DOWNGRADE（高 → 低〜中）**。⚠️ **当初の論拠は事実誤認**だった: 「掃除責任未定義による孤立参照累積」は否定される（`uninstall` は `rm -rf $GAS_DIR`（`uninstall.sh:183`）、`unbind` は purge 分岐前に `binding.json` を削除済み（`bind.sh:108-111`））。コード確認の結果、**別の実在する危害**に補正した。
- 指摘 E の permission 撤去漏れ = E の裁定で「別 finding として切り出すのが望ましい」とされた項目。

## 確定した事実（コード根拠）

### B（誤ルーティング・補正後の危害モデル）
- `account remove` で default を削除すると `accounts.sh:250-253` が残り 1 件のアカウントを default に**自動昇格**する。
- `lib/api:118-128` の default/single 経路は `accounts_resolve_default`（`accounts.sh:203-207`）が返す現在の default を**当初意図と照合しない**。binding 経路（`lib/api:99-102` の `.account` 文字列照合 → 不一致なら UNKNOWN_ACCOUNT）に相当する検証が無いため、**警告なく別アカウントへドラフト作成・ラベル・archive 等が実行されうる**。
- registry には install 時に email が記録される（`registry.sh:120,128-134`）が `account remove`（`account.sh:284-286`）はこれを走査・整理しない。`doctor` の孤立検出もカレント binding 一件に限定（`doctor.sh:197-205`）で非網羅的。
- 射程は狭い（複数アカウント + default 削除 + default 依存ディレクトリ）。データ破壊ではなく**運用・整合性負債**。

### E（permission 撤去漏れ）
- `bind`/`install` は `setup_permissions` で `settings.local.json` に allow パターンを追加（`bind.sh:72`、`permissions.sh:19-105`）。
- `uninstall` には permission 関連処理が一切なく（grep で確認済み）、パターンが**孤児として残る**。bind 固有でなく install/uninstall 全体の既存非対称。

## 実装内容

### B
1. `account remove` 実行時に (a) この削除で別アカウントが新 default に昇格する旨を警告、(b) この email を指す binding / registry エントリが N 件ある旨を事前提示（可能なら `--prune` を追加）。

### E
2. `uninstall` 時に `setup_permissions` が追加した allow パターンを `settings.local.json` から jq で除去。
