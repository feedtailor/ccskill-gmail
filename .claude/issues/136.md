## 概要

グローバル化(#121-126)でプロジェクトとアカウントの 1:1 対応モデルを解消したにもかかわらず、`install`(central 既定)と `install --dedicated` が旧モデルの導線として残っている。これらを退役し、グローバルな4本(`account add` / `skill install` / `bind` / `unbind`)＋ `api` に一本化する方針を検討する。実装ではなく、方針の確定をゴールとする議論 issue。

## 背景・動機

`install`(central)を残すことは、解消したはずの 1:1 対応モデルの温存になる。#132 で first-run 導線からは外したが、コマンド自体は残っている。「2 つの install(`skill install` と `install`)があり、違いが名前から分からない」という UX 上の混乱も、`install` を畳めば自然に解消する。

## 確定した事実(コード根拠・調査済み)

- `bind`(bind.sh)は `binding.json` の書き込みと `setup_permissions`(権限の opt-in 追加)を行う。GAS は作らない。
- `install`(central, install.sh)は上記に加えて、スキル定義を `<project>/.claude/skills/` にコピー、`<project>/.ccskill-gmail/api` を配置、registry 登録、`.gitignore` 設定を行う。固有部分はすべて「プロジェクトにファイルを置く」旧モデルの産物。`skill install`(グローバル)＋ グローバル `api` ＋ `bind` が揃った今は冗長。
- `install --dedicated` の唯一の固有価値は「プロジェクトごとに `config.js` の権限を変える」こと。だが実環境の config.js 13 箇所(共有GAS3 + 専用GAS10)を確認した結果、すべて既定(`move_to_trash` deny のみ)で、プロジェクト別権限の運用実績はゼロ。

## 検討事項(結論は出さず論点を列挙)

- `install`(central)を `bind` のエイリアスにするか、deprecated 化するか、廃止するか。
- `install --dedicated`(専用GAS新規作成)を廃止するか。既存の専用GASはレガシー解決経路で動かし続ける。
- `uninstall` の役割再定義(install 廃止後、掃除は `unbind --purge-legacy` に寄せるか)。
- `doctor` / `help` / `README` / `security-decisions` の install 言及の整理。

## 後方互換の要件

- 既存の install 済みプロジェクト(専用GAS含む)は動作不変。
- 廃止するのは「新規に作る手段」のみ。
