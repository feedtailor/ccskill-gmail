## 概要

`ccskill-gmail` の管理コマンド（`account` / `bind` / `migrate` / `install` / `uninstall` など）の実行履歴が、どこにも残っていない。記録されるのは `api` 操作（Gmail の検索・閲覧・下書き）だけで、いつ・どのディレクトリで・どの引数で `migrate` などを実行したかを後から追えない。調査用に、管理コマンドの実行履歴を監査ログとして記録する仕組みを追加する。

## 背景・動機

`migrate` を実行すると、ディレクトリは共有 GAS（`binding.json`）を使うようになるが、旧来の専用 GAS（`.clasp.json`）の痕跡はそのまま残る。実環境を調べたところ、登録済み 10 件のうち 9 件が「`binding.json` あり ＋ `.clasp.json` あり」の共存状態だった。これが想定どおりの結果なのか、いつの操作によるものかを、現状のログでは確認できない。管理コマンドの履歴があれば、こうした状態の由来を後から追跡できる。

## 確定した事実（コード根拠）

- 履歴を記録する `_ccskill_history_record` を呼ぶのは `lib/api` だけ（`lib/api:634-636`）。
- 管理コマンドは `lib/api` を通らない。`lib/api:515` のガードが `setup` / `install` / `account` / `bind` / `migrate` などを「これは `ccskill-gmail api X` ではなく `ccskill-gmail X` で実行するもの」として弾く。そのため管理コマンドの正規の実行は記録されない。
- `ccskill-gmail api unbind` のように管理コマンドを誤って `api` 経由で打つと、その失敗だけが既存ログに残る（実ログに `subcommand: "unbind"` / `error: "Unknown subcommand: unbind"` の行が存在）。正規実行は記録されないことの裏返し。
- 既存ログは `~/.ccskill-gmail/history/<email>/audit.jsonl` にアカウント別で記録し、書き込めない環境では無言でスキップする縮退設計、1000 行でローテーションする（`history.sh`）。

## 追加するもの

1. 新ファイル `~/.ccskill-gmail/history/commands.jsonl`（権限 600、アカウント非依存のグローバル 1 本）。既存 api 監査ログ（email 別）とは別ファイルにする。
2. `history.sh` に管理コマンド用の記録関数を 1 つ追加。既存の縮退設計（書き込み不可で無言スキップ）・ローテーション・ID 生成を流用する。
3. ディスパッチャ `ccskill-gmail` に記録フックを 1 箇所。管理コマンドの実行後に記録する。GAS 側・`lib/api` は変更しない。

## 記録フォーマット（commands.jsonl の 1 行）

| フィールド | 内容 |
|---|---|
| id | レコード ID（既存の生成処理を流用） |
| timestamp | ISO8601 |
| project | 実行ディレクトリ（cwd） |
| account | 解決されたアカウント。無ければ null |
| command | `install` / `account` / `bind` / `migrate` など |
| subcommand | `account` の `add` / `remove` などの二階層目。無ければ null |
| args | 残りの引数の配列（識別子・フラグ） |
| success | 終了コードが 0 か |
| error | 失敗時のメッセージ。成功時は null |
| duration_ms | 所要時間。取得できなければ null |

共通の 6 フィールド（id / timestamp / project / account / error / duration_ms）は既存 api 監査ログと同じ名前にそろえ、コマンド固有の 4 つ（command / subcommand / args / success）を新たに設ける。

記録される行の例:

```json
{"id":"20260621T150012_a1b2c3","timestamp":"2026-06-21T15:00:12+0900","project":"/Users/oishi/projects/ccskill-gmail","account":null,"command":"migrate","subcommand":null,"args":[],"success":true,"error":null,"duration_ms":4120}
{"id":"20260621T150305_d4e5f6","timestamp":"2026-06-21T15:03:05+0900","project":"/Users/oishi/projects/x","account":"work@example.com","command":"account","subcommand":"add","args":["--label","work"],"success":true,"error":null,"duration_ms":8800}
{"id":"20260621T151030_6d7e8f","timestamp":"2026-06-21T15:10:30+0900","project":"/Users/oishi/projects/y","account":null,"command":"install","subcommand":null,"args":[],"success":false,"error":"No account registered yet","duration_ms":210}
```

## 記録対象とプライバシー

- 記録するのは状態を変えるコマンドのみ: `install` / `uninstall` / `account` / `bind` / `unbind` / `migrate` / `update` / `update-all` / `skill` / `apply-config` / `setup`。
- 読み取り専用のコマンドは記録しない: `status` / `info` / `whoami` / `doctor` / `list` / `help` / `history`。多発するうえ調査上の価値が低く、ログが膨らむため。
- `args` には識別子・フラグ（email / label / path / flag）だけを残す。メール本文・件名・宛先のような機微な情報は、もともと管理コマンドの引数に含まれない。将来 `--token` のような機微なフラグが増えたら、その値を伏せる対象に加える。

設計上の補足（issue の当初案からの差分）:

- **error フィールドは終了コード由来**（`"exit code N"`）。出力本文はキャプチャしない。管理コマンドの多く（`setup` / `account add` のブラウザ起動、`uninstall` / `unbind` の Y/n 確認等）が対話的で、`tee` 等での出力捕捉はプロンプト表示の遅延・tty 判定変化で対話を壊すリスクがあるため（2026-06-22 ユーザー判断）。完了条件にメッセージ本文の要求はない。
- **account フィールドは実行時に有効なアカウント（`CCSKILL_GMAIL_ACCOUNT`）**を記録し、無ければ null。`account add` 直後の新規アカウント名を事後解決して入れる挙動は、取得が煩雑で価値が薄いため採用せず。
- `register` は issue の記録対象リストに明記されていないため記録対象に含めていない（レガシー per-project 系。退役は #136）。
