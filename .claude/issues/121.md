## 概要

ccskill-gmail を「プロジェクト単位 install」前提から、(A) ユーザースキルとしてどのプロジェクトからも使える、(B) 複数 Gmail アカウントを中央登録してデフォルト指定・プロンプトでの使い分けができる、という設計に拡張する構想。本 issue は全体方針と設計決定を記録する meta issue。実装は #122-#126 に分割する。

## 背景

現状の「1 プロジェクトディレクトリ = 1 Gmail アカウント、install 必須」には以下の不便がある:

- 任意のプロジェクトで Gmail を見たくなった時、会話を抜けて install（GAS 新規作成 + ブラウザ認可 + permission allow 処理）からやり直す必要がある
- 同じアカウントを別プロジェクトで使う場合も、毎回 GAS プロジェクトを新規作成する二度手間が発生する

## 実現可能性の根拠 (2026-06-10 コード調査済み)

- 認証トークンは既に `~/.clasprc.json` の `.tokens[<clasp_user>]` で中央管理されている (lib/auth.sh:16-97)。アカウント追加時のブラウザ認可は構造上 1 回で済ませられる
- `lib/api` はエンドポイントと clasp_user を環境変数 (`GMAIL_ENDPOINT` / `_CLASP_USER`) で注入できる設計が既にある (lib/api:45, 72)。アカウント解決は実質この 2 値であり、「解決元を SCRIPT_DIR 固定からチェーン化する」だけで核心が実現する
- CLI `ccskill-gmail` は setup 時に `~/.local/bin/` へ symlink 済み (= 既にグローバルコマンド)。ディスパッチャ (ccskill-gmail:74-125) への `api` サブコマンド追加は 1 ケースで済む

## 設計決定 (ユーザー合意済み)

1. **後方互換: レガシー install を残して共存** — 既存ユーザーは何もしなくても動き続ける。旧 `.ccskill-gmail/api` は SCRIPT_DIR のメタデータを最優先で読む解決順を維持
2. **GAS プロジェクトはアカウントごとに 1 個** — 現状の「プロジェクトごとに毎回新規作成」をやめる。MYSELF 制約 (1 エンドポイント = 1 アカウント) は不変で、変わるのはエンドポイントの粒度のみ
3. **監査ログはアカウント別に中央集約** — `~/.ccskill-gmail/history/<email>/` + レコードに account フィールド追加。レガシー環境は従来位置併用。sandbox 内で書込不可なら無言スキップ (lib/history.sh:38-47 の既存縮退設計を踏襲)
4. **環境設定の不可侵を維持** — setup/install がユーザーの `~/.claude/settings.json` 等を勝手に変更しない (確立済みの設計判断)。permission 追加は opt-in 提示のみ
5. **ディレクトリ固定は安全機能として残す** — 軽量な `bind` コマンド (binding.json を書くだけ、GAS 作成なし) を新設

## 推奨アーキテクチャ

### グローバル API エントリポイント

`ccskill-gmail api <get|post|download|save-html|save-pdf> ...` サブコマンド。ディスパッチャに `api) exec "$CCSKILL_GMAIL_DIR/lib/api" "$@"` を追加。

**不採用案**: `~/.ccskill-gmail/api` への実体配置 — permission パターンに `~` が使えず絶対パスはユーザーごとに異なるためドキュメントに固定文字列で書けない。api コピーの更新問題も再発する。`ccskill-gmail api` なら `Bash(ccskill-gmail api:*)` と全ユーザー共通で文書化できる。

### 中央アカウントレジストリ

`~/.ccskill-gmail/accounts.json` (dir 700 / file 600)。マスター直下 `.registry.json` (インストール台帳) とは寿命が異なるため分離。

```json
{
  "schema_version": "2.0",
  "default_account": "you@example.com",
  "accounts": {
    "you@example.com": {
      "label": "personal",
      "clasp_user": "...",
      "script_id": "...",
      "deployment_id": "...",
      "endpoint": "https://script.google.com/macros/s/.../exec",
      "created_at": "...", "verified_at": "...", "version": "..."
    }
  }
}
```

キーは email (プロンプトでの指名と一致)。`label` は短縮指名用エイリアス。

### アカウント解決の優先順位

```
1. --account フラグ (email / label どちらでも)
2. 環境変数 CCSKILL_GMAIL_ACCOUNT (スクリプト生成ユースケース向け)
3. cwd のプロジェクトバインド (旧 .ccskill-metadata.json / 新 binding.json)
4. accounts.json の default_account
5. 登録が 1 件のみならそれ
6. 解決不能 → {"ok":false,"error_code":"NO_ACCOUNT"}
```

### コマンド

- `account add [--label NAME]` / `account list` / `account default <email|label>` / `account remove <email>`
- `bind <email|label> [DIR]` — binding.json を書くだけの軽量バインド
- `api whoami` — 解決されたアカウントと解決根拠 (flag/binding/default) を返す
- `migrate` — `.registry.json` を email でグルーピングし、既存デプロイの 1 つをアカウント代表として accounts.json に再利用登録。**再認可不要**

### 誤アカウント操作対策

- API レスポンスのトップレベルに `account` / `account_source` を jq でマージ (jq 不在時はスキップ)
- SKILL.md に行動規範を追加: 結果報告で必ずアカウント明示 / ユーザーが指名した時のみ `--account` 付与 / 曖昧 (複数登録 + バインドなし + 不明瞭な指名) なら実行前に確認 / post は直前の get と同じ `--account` を引き継ぐ (会話途中の暗黙切替禁止)

### ユーザースキル登録

`ccskill-gmail skill install` で `~/.claude/skills/ccskill-gmail` → マスターへの symlink (git pull だけで最新化、コピー更新問題が消える)。symlink 不可環境用に `--copy`。

ドキュメント正本は 1 セットのみ: グローバル表記 (`ccskill-gmail api`) はバインド解決によりレガシープロジェクト内でも正しく動くため、プロジェクト版との二重管理は不要。

**2026-06-10 検証で前提を修正** (詳細は #122 に記録): 同名スキルは**ユーザースキルがプロジェクトスキルを上書き**する (公式 docs "personal overrides project"。当初仮説と逆)。つまりユーザースキルを登録した人は、レガシー install 済みプロジェクトでも新表記の SKILL.md が適用される。これが成立するのは lib/api の cwd フォールバック (#122) があるからであり、**Phase 1 の cwd フォールバックは後方互換の生命線**。ユーザースキルを登録しない既存ユーザーは従来どおり変化なし。

## 要検証事項 (#122 の冒頭で claude-code-guide により裏付けを取る)

→ **2026-06-10 検証完了。結果は #122 に記録。** 要点: (1) 同名スキルはユーザー側が優先 (仮説と逆、上記の修正参照)、(2) allow ルールは確認プロンプトのスキップのみで sandbox 制限は残る (home への書込縮退が主経路になる)、(3) `allowed-tools` の `Bash(cmd *)` パターンは有効 (プロンプトスキップのみ)。アーキテクチャ自体は 3 点とも崩れない。

1. プロジェクトスキルとユーザースキルが同名のときの優先・共存挙動 (後方互換戦略の前提)
2. permissions の allow ルールにマッチした Bash コマンドと sandbox の関係 (home への履歴書込・トークン書き戻しが通る条件)。設計検討時のエージェントは「allow で sandbox 外実行」と主張したが**未裏付け**。結果次第で履歴書込の縮退頻度の見積りが変わる (機能自体は縮退設計で成立)
3. skill frontmatter `allowed-tools` での `Bash(ccskill-gmail api:*)` パターンの有効性

## トレードオフ (README に明記予定)

- アカウント単位 GAS への集約により、config.js (permissions allow/deny) もアカウント単位になる。プロジェクト別に権限を絞る上級ユースケースはレガシー install で引き続き可能
- グローバル利用時の POST 用 tmp JSON は cwd 相対 `.ccskill-gmail/tmp/` を維持 (api が実行時に mkdir)。$TMPDIR 案は Write ツールの permission パターンが絶対パスになり文書化不能のため不採用
