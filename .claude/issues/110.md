## 概要

プレーンテキスト（`text/plain` のみ）で送られてくるメールに対して `save-pdf` / `save-html` / `get_message_html` を実行すると、改行・等幅前提の罫線文字（`━━`, `───` 等）・全角スペースによる桁揃えがすべて崩れた HTML が返り、PDF 化結果が読みづらくなる。

Gmail UI 上は同じメールを等幅・改行保持で綺麗に表示しているため、ユーザー体験との乖離が大きい。実際の経理ワークフロー（領収書 PDF 保存）でこの差が表面化した。

## 具体的事例

2026-05-09 にユーザーが「お名前.com の領収書」を経費 PDF として保存しようとした際に発生。

### 対象メール

- 件名: `[お名前.com]ドメイン更新 料金ご請求／領収明細 27695284`
- From: `"お名前.com" <admin@onamae.com>`
- 形式: **プレーンテキストのみ**（HTML パートなし）
- 特徴:
  - `━━お名前.com by GMO ━━━━━━━━` のような罫線文字で section を区切る古典的な日本企業向け業務メール
  - 全角スペース + ドット (`ご請求書番号................：27695284`) で項目を桁揃え
  - 改行で段組を維持

### 期待動作（Gmail UI 上の見え方）

```
━━お名前.com by GMO ━━━━━━━━━━━━━━━━━━━━━━━━

───────────────────────────────────
■ドメイン更新料金ご請求明細／領収書■
───────────────────────────────────

[明細情報]
ご請求書番号................：27695284
請求書発行日................：2026年05月02日
お支払い金額合計（税込）....：2,194円
組織名......................：株式会社フィードテイラー
```

### 実際の動作（save-pdf 結果）

改行が無視されて 1 段落として連結され、罫線・桁揃えがすべて潰れた状態で PDF 化される。経理書類としてそのまま保存するには見栄えが悪く、目視確認時に明細項目が探しにくい。

## 原因

`gas-template/handlers/read.js` の `handleGetMessageHtml`（[L164](../../../gas-template/handlers/read.js)）が `message.getBody()` の戻り値をそのまま HTML として返している点に由来する。

```js
var html = message.getBody();
// ...
html = headerHtml + html;
```

GmailApp の `getBody()` はプレーンテキストメールに対しても HTML らしき文字列を返すが、テキストの改行を `<br>` に変換せず、また `<pre>` などで `white-space: pre-wrap` を指定していないため、ブラウザ・headless Chrome 上では:

- 改行 (`\n`) が空白に丸められる
- 連続する全角スペースは 1 文字分に潰れる
- 罫線文字は折り返されて格子が崩れる

結果として、HTML パートを持つリッチメールは綺麗に表示できるが、プレーンテキスト onlyのメールが事実上レイアウトロスする。

`save-html` / `save-pdf` は内部的にこの `get_message_html` の結果を使うため、影響範囲は 3 アクションすべて。

## 改善策

プレーンテキストメールを検出した場合、本文を等幅・改行保持の `<pre>` でラップして返す。

### 検出方法（GAS 側）

GmailApp の API では、HTML パートが存在しないメールは `getBody()` と `getPlainBody()` がほぼ同一になる傾向があるが、これは保証されない。確実な検出には **Gmail Advanced Service** から MIME structure を取って `text/html` パートの有無を見るのが正攻法。簡易版としては、`getBody()` の結果に HTML タグがほぼ含まれない場合（例: タグ密度が極端に低い、`<html>` / `<body>` / `<div>` / `<p>` のいずれも出現しない）にプレーンテキストとみなす検出でも実用上十分。

判定優先度:

1. Gmail Advanced Service による MIME parts inspection — 確実だが API 有効化が必要
2. `getBody()` 内のブロックレベル HTML タグの有無による heuristic — 設定変更不要・既存 GAS 範囲で完結

第一弾としては (2) で着手し、誤検出が出る場合に (1) に切り替える方針が現実的。

### ラップ方式

検出後、HTML を以下のようにラップする:

```html
<pre style="white-space: pre-wrap; word-wrap: break-word; font-family: ui-monospace, SFMono-Regular, 'Menlo', 'Consolas', 'Noto Sans Mono CJK JP', monospace; font-size: 13px; line-height: 1.5; margin: 0;">
{escaped plain body}
</pre>
```

ポイント:

- `white-space: pre-wrap` で改行と連続スペースを保持しつつ、極端に長い行は折り返す
- 等幅 CJK 対応フォント（`Noto Sans Mono CJK JP` 等）を含めて罫線文字 (`━`, `─`) と全角スペースの桁が揃うようにする
- 本文は `escapeHtml_` で HTML エスケープしてから流し込む（XSS 対策と、`<` を含むテキストの保護）
- ヘッダ部 (`From: ... To: ...`) は従来通り sans-serif の `<div>` で出し、本文だけ `<pre>` 化する
