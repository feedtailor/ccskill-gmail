## 概要

`gas-template/utils/gmail.js` の `formatThread()`（`search` アクションで使うスレッド一覧用フォーマッタ）は `from` に `firstMessage.getFrom()`（スレッド最初のメッセージの送信者）を返す。実装として正しいが、利用側は「このスレッドは今誰が動いている状態か」を知りたいことが多く、`from` を「直近の送信者」と誤解しやすい。既存の `from` は変更せず、下書きを除いた直近メッセージの送信者を表す `lastFrom` を追加する。


## 出典

- 他プロジェクト（artifact-dashboard）側のエージェントAIからの提案（2026-07-08）。毎朝ダッシュボードの Gmail 欄で「要返信」一覧の送信者表示が、実際にはユーザ自身がスレッドを開始した際の宛先（＝自分自身）になっており、誰に返信すべきか分からない表示になっていたとのユーザ指摘が発端。
- 提案元の調査で `ccskill-gmail` 側の実装自体は `firstMessage.getFrom()` という関数名通り正しい挙動であり、`artifact-dashboard` 側が「`search` の `from` ＝直近送信者」という誤った前提で使っていたことが原因と判明（バグではない）。
- この提案を受け、`ccskill-gmail` 側で実コード（`gas-template/utils/gmail.js` 12-31行目）と `reference/triage.md` を確認し、以下を独自に検証した。


## 詳細

### 既存実装の確認結果

`formatThread()` は提案の記述通り `from: firstMessage.getFrom()` を返す（意図通りの実装、バグではない）。

### 類似の先行issue（#098）との整合

2026-04-14 対応の #098 で、`get_thread` 用の `formatThreadWithMessages()` に、下書きを除いた直近メッセージを表す `lastSentMessage` と `hasDraft` を追加している。理由は「`messages[-1]` や `from` を素で読むと最終アクター判定を誤る」という実際の事故（下書き作成直後のスレッドを "返信済み放置" と誤判定し一括アーカイブしかけた）だった。今回の `lastFrom` は、この設計判断を軽量な `search` 側にも一貫して適用するもの。

### この改修が ccskill-gmail 自身の運用にも効く根拠

`.claude/skills/ccskill-gmail/reference/triage.md`（121-130行目）に、現行のトリアージ手順が明記されている。

```
search で候補スレッドを取得
  → 各スレッドごとに get_thread を呼んで lastSentMessage.from を確認する
    （messages[-1] は使わない、search の from は使わない）
```

つまり `search` の `from` が「最終アクター」判定に使えないため、トリアージのたびにスレッド数分の `get_thread`（本文・添付込みの重い API）呼び出しが発生している。これは artifact-dashboard が抱えていた問題と同じ構造であり、`ccskill-gmail` 自身の標準ワークフローにも及んでいる。`search` に `lastFrom` を追加すれば、この1次選別が `search` 1回で完結するようになる。

### なぜ get_thread を件数分呼ぶのでは代替にならないか

| | 内容 | 呼び出し回数 |
|---|---|---|
| `search` | 複数スレッド分の軽量なサマリ | 1回でまとめて取得 |
| `get_thread` | 1スレッド分の全メッセージ本文・添付ファイルまで含む重い詳細 | スレッドごとに1回 |

一覧 UI や定期トリアージで直近送信者だけが欲しい場合に `get_thread` を件数分呼ぶと、同一 GAS デプロイへの同時多発リクエストになりうる（`ccskill-googlecalendar` #016 で実証済みの構造的リスクと同種）。加えて本文・添付情報まで毎回取得するのは明らかに過剰。よって「直近送信者」は `search` が1回で返す軽量なレスポンスに最初から含めておくのが構造的に正しい。

### `lastSentMessage` との差分（意図的な設計判断）

提案側の参考実装は「全メッセージが下書きの場合は最後のメッセージ（下書き）の送信者にフォールバックする」実装だったが、本実装では #098 の `lastSentMessage` と同じく **全て下書きの場合は `null`** とする。フォールバックすると、下書きの送信者（＝ユーザ自身のことが多い）を「直近の実送信者」であるかのように見せてしまい、誤解を再生産するため。API 全体の一貫性の観点からも #098 の前例に揃える。


## 方針

- `formatThread()` に `lastFrom` フィールドを追加する（既存の `from` は変更しない、後方互換の拡張）
- `lastFrom` の定義は `formatThreadWithMessages()` の `lastSentMessage` と同じ考え方（下書きを除いた直近メッセージ）の送信者に揃える。ただし `lastSentMessage` のようなメッセージオブジェクト全体ではなく、`from` と対をなす軽量な文字列のみを返す
- 全メッセージが下書きの場合は `null` とする（`lastSentMessage` の前例に合わせる。ラストメッセージへのフォールバックはしない）


## 実装内容

`gas-template/utils/gmail.js` の `formatThread()`:

```javascript
function formatThread(thread) {
  const messages = thread.getMessages();
  const firstMessage = messages[0];
  const lastMessage = messages[messages.length - 1];

  // Drafts appear inline with sent messages; skip them to find who actually
  // last acted (same convention as lastSentMessage in formatThreadWithMessages).
  var lastRealMessage = null;
  for (var i = messages.length - 1; i >= 0; i--) {
    if (!messages[i].isDraft()) { lastRealMessage = messages[i]; break; }
  }

  return {
    id: thread.getId(),
    subject: stripInvisibleChars(firstMessage.getSubject()),
    from: firstMessage.getFrom(),
    lastFrom: lastRealMessage ? lastRealMessage.getFrom() : null,
    date: lastMessage.getDate().toISOString(),
    messageCount: messages.length,
    isUnread: thread.isUnread(),
    isImportant: thread.isImportant(),
    isInPriorityInbox: thread.isInPriorityInbox(),
    isInInbox: thread.isInInbox(),
    labels: thread.getLabels().map(function(label) {
      return label.getName();
    })
  };
}
```

- 追加コストはループ1回のみ（`thread.getMessages()` は既存コードで取得済みのため追加 API 呼び出しなし）
- 単体テストは `tests/lib/test-strip-invisible-chars.js` と同じ手法（`new Function` で GAS の関数を Node 上に抽出し、モックの thread/message オブジェクトで検証）を使う。GAS のライブ API 呼び出しは不要
