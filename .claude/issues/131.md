## 概要

`status` / `update-all` / `info` は、ユーザレベルのセットアップ（`binding.json` だけで専用 GAS を持たない構成）のディレクトリを、いつまでも最新でない（`status` の表示では `outdated`）と誤判定し、`update-all`（専用 GAS を個別に追従更新する操作）を促す。版数の判定を構成の種別ごとに分け、専用 GAS のレガシー install が残っているときは `update-all` 一辺倒でなく `migrate`（集約）を促すようにする。

## 多エージェント議論の裁定 (2026-06-16)

指摘 A はコードを読んで全面的に裏づけられた実在の欠陥で、対応指摘として残す（裁定は KEEP）。ただし重大度は「最高」から「高」に下げる。データ破壊やセキュリティへの影響はなく、api 本体（検索・閲覧・下書き）は正常に動くため。`status` / `update-all` / `info` をユーザーが自分で実行したときだけ表面化する、表示と誘導の不具合である。

## 確定した事実（コード根拠）

- ユーザレベルのセットアップの install は `install.sh:126-236` の経路で完結し、`.ccskill-metadata.json` を書かない（メタデータ生成は専用 GAS 用の `install.sh:417` だけ）。
- `registry_upsert` は metadata が無いとき `version="unknown"` を記録し続ける（`registry.sh:108`）。
- `MASTER_VERSION` は git の短縮 HEAD（`VERSION` ファイルは存在しない）。`"unknown"` との一致は原理的に起こらない。
- `status.sh:194` / `update-all.sh:85` / `info.sh:107` は version 文字列を単純一致で見るだけで構成の種別を区別せず、ユーザレベルのセットアップを最新でないと誤判定し続ける。
- `update.sh:283` の分岐は `registry_upsert` をやり直すが metadata を書かないため version は `"unknown"` のまま変わらない。一方で直後の `L290` は「Updated to version: …」と実際の版を表示しており、食い違っている。
- `update-all.sh:151-154` は `deployment_id` が無いことを理由に、手動デプロイが必要なものとして扱い、`L187-204` で「GAS エディタで手動デプロイ」と誤って案内する（`update.sh:274` の「共有 GAS は account update が管理する」という方針と矛盾）。

## 実装内容

1. registry のエントリに構成の種別（ユーザレベル / 専用 GAS）を持たせる。または `binding.json` の有無で判別する（`update.sh:272` が既にこの条件を使っている）。
2. `status` / `update-all` / `info` / `update` の版数比較を種別ごとに分ける。ユーザレベルのセットアップは版数比較の対象から外し、表示で `shared` / `per-project` を区別する。
3. `update-all.sh:151-154` の `deployment_id` 空判定を、ユーザレベルのセットアップでは、手動デプロイが必要なものに含めない。
4. 専用 GAS が残っているとき、`status` の案内を `update-all` 一辺倒でなく `migrate`（集約）を主にする。`update-all` の案内は個別運用を続ける人向けに残す。
5. 旧来の `.ccskill-metadata.json` を最優先で解決する後方互換の経路は壊さない。
