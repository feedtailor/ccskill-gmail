## 概要

`ccskill-gmail update-all` と対称になる **`ccskill-gmail uninstall-all`** が存在しない。

`ccskill-gmail` ディスパッチャ (`ccskill-gmail:37–39`) のヘルプは:

- `uninstall [DIR]` — 単一プロジェクトをアンインストール
- `update-all` — 全インストール先を更新

…と非対称で、登録済みの全プロジェクトから一括でアンインストールする手段が無い。複数プロジェクトを試した後の片付けや、別マシンへの引っ越し前にまとめて剥がしたい場合に手作業が増える。

## 提案

`commands/uninstall-all.sh` を新設し、`update-all.sh` (`commands/update-all.sh:1–195`) と同じパターンで実装する。

### 動作仕様

1. `registry.sh` から登録済みインストール一覧を取得（`update-all` と同じロジック）
2. 対象を分類:
   - 通常の対象（`.ccskill-gmail/` が存在）
   - **存在しない (already gone)** — registry には残っているがディレクトリ/インストールが消えている → registry のクリーンアップ対象としてレポート
3. 対象一覧を表示し **Y/n で確認**（`update-all` 同様）。`update-all` よりも破壊的なので、デフォルトを **N** にする（`-n 1 -r` の判定を逆転）
4. 各対象で `commands/uninstall.sh --yes <path>` を順次実行（`--yes` フラグが uninstall.sh 側で必要なら追加実装する。現状の `uninstall.sh` を確認して合わせる）
5. サマリー表示: 成功件数 / 失敗件数 / 既に存在しなかった件数
6. **GAS プロジェクト本体は自動削除しない** 旨の注意書きを末尾に表示（[script.google.com](https://script.google.com) からの手動削除を案内）。これは `uninstall` 単体の挙動と同じだが、一括版だと忘れやすいので強調する

### CLI 配線

- `ccskill-gmail` ディスパッチャの `update-all)` の隣に `uninstall-all)` を追加 (`ccskill-gmail:87–88` のパターン)
- ヘルプテキスト (`ccskill-gmail:37–39` 周辺) にも追記

### オプション

- `--yes` (`-y`): 確認プロンプトをスキップ（CI / スクリプト用途）
- `--dry-run`: 対象一覧の表示のみで実行はしない

## 設計判断

- **個別 `uninstall` の挙動は変えない** — 一括版は薄いラッパーに留める
- **registry からエントリ削除する責務は `uninstall.sh` 側に既に存在するはず** なので、一括版で別途登録解除のロジックを書かない（DRY）
- **GAS プロジェクトの一括削除はしない** — clasp で削除する手段はあるが、誤操作の影響が大きすぎる。本 issue のスコープ外

## クローズ判断 (2026-06-22)

**クローズ。本 issue の設計では実装しない。目的は #140 が別の形で達成済み。**

本 issue は per-project install を複数登録した世界を前提に、`registry.sh` を巡回して各プロジェクトから一括アンインストールする（`update-all` と対称の）`uninstall-all` を構想したもの。その後の central 化（#121〜#126）で前提が変わったため、当初設計は陳腐化した。

- central 化により「片付け対象」が各プロジェクトの `.ccskill-gmail/` から中央レジストリ `~/.ccskill-gmail/`（accounts.json / gas / history）+ ユーザースキル + CLI symlink に集約された。registry を巡回して per-project install を剥がすという本 issue の前提自体が消えている。
- 本 issue の動機（「複数プロジェクトを試した後の片付け」「引っ越し前にまとめて剥がす」）は、#140 で実装した `ccskill-gmail uninstall --all`（central 形のフル撤去。`setup` と対称）がより適切な形で満たしている。#140 自身も本 issue を「旧 per-project モデル・参考」と明記している。
- per-project install は #136 で退役予定のレガシー。残る論点「併存している複数の per-project install をまとめて剥がす手段」は per-project 退役（#136）のスコープに含めるのが自然で、本 issue で別途扱う必要はない。
